## M1 — worker.py (F1, F2, F6) verified live, 2026-08-16

Tested with real primary + standby processes against the live cluster, real `kill -9`, no mocking:

- **F1 (transactional step-loop):** verified. Killed a worker mid-word during real Claude Opus 5 streaming; `job_state.step` stayed put, `partial_output` held exactly the flushed prefix (nothing beyond the last completed ~1s chunk), and a fresh process resumed and continued the sentence with no repeated or dropped text (`"...the th"` + `"undering-herd..."` → coherent, zero loss observed in that run).
- **F2 (lease + standby failover):** verified with a live standby process, not a manual restart. Found and fixed two real bugs in the process, not simulated:
  1. **Unhandled `SerializationFailure`** — concurrent primary/standby access to the same `lease` row under CockroachDB's SERIALIZABLE isolation threw `WriteTooOldError` and crashed the primary outright. Fixed with `db.run_txn()`, a retry-with-backoff wrapper (SQLSTATE 40001 is CockroachDB's documented client-retry contract, not an error condition) — now used by every write path in `worker.py`.
  2. **False eviction risk** — the lease was only renewed once per loop iteration plus on each chunk flush; a step with long "thinking" latency before its first token (observed: several seconds) could outlast `LEASE_TTL_SECONDS` before any flush happened, letting a live standby steal the lease from a healthy primary. Fixed with a background heartbeat thread (`_lease_heartbeat`, daemon, renews every `LEASE_HEARTBEAT_SECONDS` independent of streaming) — a `SIGKILL` takes the whole process down including the thread, so a real death still expires the lease normally; a live process never gets falsely evicted (confirmed: 10s+ of normal operation with no false claim).
  - **Measured failover timing** (single dev-machine sample, not a rehearsal): lease claim at +2.1s after kill, first standby token at +5.0s — right at the F2 acceptance bar. Tightened `LEASE_TTL_SECONDS=2`, `LEASE_HEARTBEAT_SECONDS=0.5`, `STANDBY_POLL_SECONDS=0.25` (brief's own prescribed first remedy for "failover exceeds 5s"). The remaining latency is mostly the model's own thinking/first-token time even with `output_config={"effort":"low"}` wired in — this needs re-measurement during the real Feature-Freeze demo rehearsal (3x cold, per Section 1.6), not just this dev sample, before trusting it live. Pre-approved fallback if it stays flaky: node-kill/single-region variant (2h cost, already in the brief's pivot triggers).
- **F6 (ephemeral/amnesia mode):** verified. `--no-memory` writes nothing to CockroachDB (`jobs` count unchanged across two separate runs) and every invocation starts fresh at step 1 with the amnesia banner, by construction (nothing persisted to resume from).
- **F5 (streaming terminal output):** implicit in the above — every run streamed live tokens with `[STEP n/20] [region]` labels throughout.
- **F3 (research pipeline, full run, M1 exit criterion):** run start-to-finish, unattended, against the live cluster. **5.64 minutes total** — slightly over the brief's 3-5 min target (~13% over). Step boundaries landed exactly as designed: step 11 hit `doc_10_wal_crash_recovery.md` precisely (confirmed in the transcript), and the step-20 closing synthesis genuinely integrated all 10 corpus findings into one coherent, well-reasoned answer to the research goal — quality is strong. 20/20 `memory_events` rows written (1 plan + 10 findings + 9 syntheses), 175 `output_chunks`. If the 5-min ceiling matters for the actual demo pacing, the lever is `STEP_MAX_TOKENS` (currently 1500) — not yet tuned down, since output quality/coherence seemed worth the extra ~40s.
- **F4 (curated corpus + seed memories):** verified both halves. Corpus: 10 docs in `corpus/`. Seed memories: `scripts/seed_memories.py` inserts 5 curated, disclosed (`curated=true`) memory rows under a dedicated seed job with real embeddings; a live vector-similarity test (`embedding <-> query_vec`) correctly ranked the write-ahead-logging seed memory as the closest match for "how do databases survive crashes without losing data?" — confirms the recall mechanism F8 will build on is semantically sound, not just structurally present.

## M2 — arena.py (F7, F8, F9) verified live, 2026-08-16

- **F7 (brain monitor):** verified. `monitor.py` opens a CockroachDB core changefeed (`EXPERIMENTAL CHANGEFEED FOR memory_events WITH resolved='1s'`, no sink, no enterprise license needed) streamed row-by-row via `psycopg`'s `cursor.stream()` — confirmed live: a real insert from a second connection appeared on the SSE feed within the capture window (well inside the ≤2s acceptance bar). One background thread owns the changefeed for the whole app and fans events out to every connected SSE client (`arena.py`'s `_broadcast_loop` + a per-client `queue.Queue`), not one changefeed connection per browser tab — avoids a thread-per-connection leak and matches F10's "one shared arena" design. Config-driven fallback to 1s polling (`MONITOR_MODE=poll`, or automatic if the changefeed fails to open) per the brief's own Failure States section — same pattern as the LLM/embedding provider switches. **Panel survives the worker kill:** ran a real worker job, watched real `memory_events` rows arrive on the SSE stream, `kill -9`'d the worker mid-step — the SSE connection and the arena server stayed up throughout (architecturally guaranteed: the monitor reads only from CockroachDB, never from a worker process). The changefeed payload's `embedding` field (384-1024 floats) is stripped before it reaches the client — the panel never needs it.
- **F8 (recall):** verified, with a real design change forced by live measurement. First implementation vector-searched `memory_events` (`embedding <-> query_vec`, top-`RECALL_TOP_K=5`) and then asked the model (via the shared `llm.step_stream`, same Claude Opus 5 + `effort:low` path as the research pipeline) to synthesize a 2-4 sentence answer grounded in the retrieved rows. Measured against the real Anthropic API: **3.2-4.6s across 5 samples, never once under 3s** — first-token latency alone was 1.2-1.7s (thinking-token overhead the brief's own model guidance forbids disabling) and reducing `max_tokens` didn't reliably help. This misses F8's explicit `<3s` acceptance bar, so the design changed: the "answer" is now the top-ranked row's `content` verbatim (findings/syntheses are already "one detailed paragraph" of flowing prose per `research.py`; seed memories are curated full sentences) — no LLM round-trip. Re-measured steady-state: **0.3-0.7s** (embed + vector search only), 5 provenance rows returned, correct top match (write-ahead-logging seed memory ranked first for "how do databases survive crashes without losing data?", matching the M1 seed-memory verification). One-time cold-start cost (~4s, `sentence-transformers` model load) happens once per process, not per query.
- **F9 (Managed MCP Server):** verified end-to-end. Retrieved the cluster's real MCP connection details from the CockroachDB Cloud console (Connect → Model Context Protocol tab, not previously recorded anywhere in this repo) and ran `claude mcp add cockroachdb-cloud https://cockroachlabs.cloud/mcp --transport http --header "mcp-cluster-id: 23cd98bf-ac92-4131-9de4-cb182650fb93"`, then `claude mcp login cockroachdb-cloud` (OAuth; the CLI needs a real TTY for the callback — `script -q /dev/null claude mcp login cockroachdb-cloud` was used to get one). Granted **Read Data only** (Write Data left unchecked in the consent screen) — matches the read-only intent already recorded in this file. Ran one real read-only query through the connected tool (`mcp__cockroachdb-cloud__select_query`) from a fresh `claude -p` process scoped to this directory: `SELECT id, job_id, region, step, kind, ts, source, curated, left(content, 80) AS content_excerpt FROM memory_events ORDER BY ts DESC LIMIT 5` — returned real rows matching the same table the arena/recall endpoints read (Beat 4's "two-second cut: same rows queried raw through the Managed MCP Server"). This query also caught a real bug: a stray `worker.py` process from an earlier F7 test outlived its intended `kill -9` (wrong PID captured through `nohup ... &`) and had pushed a live job to step 18/20 unsupervised — found via this MCP query, killed, and its rows deleted. The connection is registered project-scoped to this directory in `~/.claude.json` (machine-local, not committed — matches how the other MCP servers in this environment are configured); reconnecting on a new machine means re-running the two commands above.

**Recall/monitor demo data:** left clean at 1 job (the curated seed job), 5 `memory_events` rows — no stray test data from this session's verification runs.
